# 色彩与渲染：用于修图决策的边界

先用这些原则解释图片，再用当前 LightCraft 的控件及预览验证。这里的摄影建议属于综合判断，不是每张图必然成立的因果结论。源码事实、建议和实测的等级见 [来源](sources.md) 与 [验证记录](validation.md)。

## 1. 分清“颜色在哪里”

| 概念 | 对修图的实际影响 |
|---|---|
| 基色、白点、编码/传递函数 | 都是色彩解释的一部分；同样的 RGB 数字，在不同解释下不代表同样颜色 |
| 场景参考与显示参考 | 场景值描述捕捉到的相对光；显示变换决定如何放进屏幕亮度和色域。场景参考不等于所有数据都线性，显示参考也不等于只有 sRGB |
| 输入、工作、输出空间 | 相机输入解释、编辑运算空间与交付空间分工不同，不能用“换成某空间”代替调色 |
| 白平衡与色适应 | 关系到照明和观察白点；不能把场景里的所有物体都变中性 |
| 色域映射与裁切 | 把超出显示范围的颜色直接截断，可能改变色相、丢层次；低强度或分区调整有时比全局硬拉更稳妥 |

Colour 的 `RGB_Colourspace`、适应变换和色差实现用于确认术语及数值比较条件；OCIO 的 reference space / view transform / look 用于区分技术转换和创意效果。它们不要求安装这些库，也不代表 LightCraft 暴露任意 OCIO 管线。

LightCraft 0.13.0 源码描述的 CPU 管线以线性 Rec.2020 为输入；白平衡/曝光等场景运算、明暗映射、感知色彩调整、输出编码和曲线分阶段处理。**界面操作顺序不等于改变内部管线顺序**。重复应用会改写设置的操作，仍可能覆盖先前调整。

## 2. 曝光、明暗和恢复余量

- 整图暗可能来自拍摄、显示映射、故意保留的夜景，或已有风格。先看主体和意图，不自动把平均值拉到中灰。
- 曝光类调整会影响大量区域；只有脸部/前景需要改善时，先评估蒙版、阴影或其他局部手段。判断改善的同时看重要高光是否失去层次。
- LightCraft 的曝光是增益，但经后续色彩、曲线、色域和输出处理后，画面的颜色观感也可能变化；不要承诺曝光变化完全不影响色彩。
- 后期加曝光不能补回拍摄时没捕捉到的光子，不能据此承诺噪声降低。提暗部后应检查噪声、色块、纹理和带状断层。
- JPEG/预览里的白块，只证明当前渲染接近输出上限；既不能证明传感器已剪切，也不能证明 RAW 一定可恢复。应通过适度降曝光/高光、查询源格式和查看结果进一步判断。
- RAW 容器、位深标签或“浮点管线”均不保证特定相机文件的真实传感器数据已成功解码。检查 `previewOnly` 等状态；预览回退不能当作完整 RAW 显影。

## 3. 白平衡与局部色偏

| 观察 | 要进一步区分什么 | 可以尝试 | 看什么决定保留 |
|---|---|---|---|
| 灰/白参照系统性偏色 | 它是否真的中性、是否受有色光照明 | 按主要光源小幅 WB，必要时比较局部修正 | 参照和主体合理，现场氛围保留 |
| 室内外区域各自偏色 | 混合光而非一个全局白点错误 | 先定主光，再局部蒙版修正另一光源区域 | 不为救一块区域破坏其他区域 |
| 金色时刻皮肤偏暖 | 暖光还是不希望的偏橙 | 保留暖光，仅修正过强的局部色相/彩度 | 肤色与光线一致，未变灰或失去血色 |
| 夜景有蓝/绿/洋红光 | 场景光源还是解码/处理异常 | 明确想保留哪些光源，局部处理问题区域 | 保留夜景层次与光源区别 |

白云、白衣、眼白都不是自动成立的灰卡。没有已知参照、受控光源和合理显示条件时，措辞应是“观感更自然/符合目标”，而不是“已校准”或“绝对色准”。

LightCraft 的 WB 可能是相机相关 Kelvin，也可能是相对于基准的标度；`values` 与 `settings.wb` 还涉及 `scale` 语义。操作前读 [参数说明](lightcraft-operations.md)，保留当前 mode/scale。不要从别的软件复制 K 值，也不设统一肤色 RGB。

## 4. 彩度、色相、局部对比与细节

- 感知空间把明度、彩度、色相分开，有助于思考“想改哪一项”，但实际工具仍会产生交互和色域限制。LightCraft 的 mixer/grading 作用与现有参数以实时控件为准。
- 肤色偏红可能是光线、WB、全局饱和、局部调色或颜色映射；“肤色偏红→一律降低橙色饱和”不成立。先观察其他中性色和相邻区域，选择最小影响的控制。
- 天空/霓虹过艳不必整图去饱和；先看相应色相、高光与输出色域。若高光色相已漂移，还需考虑明暗与通道关系。
- 清晰度、纹理、去雾和锐化并非可互换的“变清楚”。放大检查轮廓光晕、皮肤质感、噪声和颗粒；参考图中的景深、镜头特性或拍摄运动模糊，不能靠这些控件承诺复制。
- 降噪/锐化在整体风格确定后再做针对性检查；100% 细节与最终交付尺寸各看一次。不为了更平滑抹掉纹理，不把额外胶片颗粒当传感器噪声修复。

## 5. LUT：先核对输入契约

对外部 LUT 至少确认：期望的基色/白点、linear/log/display 编码、数值域、输入/输出范围，以及它是技术转换、创意 look 还是两者合一。缺少这些信息就不能承诺正确套用。

优先查随附文档；缺信息时把问题合并为一次：这个 LUT 期望什么输入色域和编码、输出到哪里，是技术转换还是创意风格，以及希望参考什么效果？`.cube` 的标题、注释和 DOMAIN 数值只能提供线索，不能替代输入契约。若输入链不匹配，先说明限制，可按可见参考做明确标注的视觉近似，不直接导入后宣称匹配。创意 LUT 可以有意染色或改变中性色，不能用“灰阶必须保持中性”作为所有 LUT 的验收标准。

OCIO 的 look 有指定处理空间，LUT 采样可能需要 shaper；这说明“都是 `.cube`”并不表示输入兼容。避免重复执行已经包含在 LUT 或现有流程中的技术转换；也不把单次转换原则误写成“所有创意曲线只能一条”。

**LightCraft 0.13.0 的实际边界（源码确认）：**

- `profile.import` 可把 3D `.cube` 导入为创意 profile，列出 profile 后按真实 ID 选择和调 Amount。解析器拒绝 `LUT_1D_SIZE`；支持 `DOMAIN_MIN/MAX` 并不代表能推断相机 log 或自动转换色彩空间。
- LUT 在收尾阶段接收显示编码后的颜色，位于输出色域映射、编码、曲线和颗粒之后；不能把为相机 log 或场景线性值设计的 LUT 直接当兼容输入。
- 默认预览与其他输出空间可能给出不同 LUT 输入；如果使用 LUT，要在实际输出条件下同时看预览与导出。HDR 分支也不能视为完整 HDR/ACES 技术变换支持。
- Raw-Alchemy 的 RAW→线性工作空间→特定 log→创意 LUT 链条属于另一项目。t3mujinpack 的 darktable 风格依赖相应模块。二者都没有在此 Skill 中被安装或转换成 LightCraft 预设。
- 需要严格的 log/ACES/OCIO 管线而现有工具未证明支持时，说明差距；提供兼容的视觉近似或另行研究方案，不擅自换软件或制作所谓“等价”转换。

## 6. 比较与交付

1. 原始外观、本轮基线、参考图和候选版本分别标识；保护用户已有的编辑。
2. 色调 A/B 使用一致的输出空间、显示变换、尺寸和裁剪。若目标包含裁剪，构图与同区域颜色分别比较。
3. 先看全图目标，再看关键局部；100% 需要足够分辨率的渲染或应用内放大，不能把已缩小的 1024 像素图再放大当作原片细节。
4. 若使用直方图，先确认统计对象/范围；若计算色差，确认参考、profile、白点、标度和公式。指标用于发现特定变化，不用于给审美或肤色真实性自动打分。
5. 导出的格式、位深、色彩空间、ICC、尺寸与查看器解释分别检查。发现预览与成品不一致时，先排查输出条件、profile、LUT 和渲染路径，再继续改图。
6. 没有显示器校准或色卡证据时，不宣称专业测色验证；真实摄影样例未完成时，不把合成演示库的成功当作真实人像/相机色准证明。
